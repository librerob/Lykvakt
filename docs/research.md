# Research and product decisions

Research date: 24 October 2026. Sources below are project code, maintainer documentation or advisories. This is a targeted review, not a competitor audit. A documented feature is not proof that it works on every device; an unverified property is not an absent feature.

## User problems and evidence quality

The original Authenticator [Chrome troubleshooting documentation](https://github.com/Authenticator-Extension/authenticator.cc/blob/master/docs/en/chrome-issues.md) warns that reinstalling clears data. Its [discussion index](https://github.com/Authenticator-Extension/Authenticator/discussions) includes reports titled “Exports inconsistent?” and “after Imported the backup file, the 2FA's digists does not work correctly,” plus requests to edit initial HOTP counters. These are user reports, not reproduced root causes or prevalence estimates. They justify exact-parameter migration tests, preserving counters, and never suggesting reinstall as recovery.

Aegis’ [FAQ](https://github.com/beemdevelopment/Aegis/blob/master/FAQ.md) documents why device changes can invalidate biometric key access and why users need password reminders. 2FAuth explicitly documents APP_KEY loss as unrecoverable. These are concrete recovery constraints. We found no defensible comparative dataset for interface simplicity, lost-account frequency or autofill success rates; none is claimed.

## Website awareness

[2FA Notifier](https://2fanotifier.org/) already compares visited websites with a known support list and links users to setup documentation; [source](https://github.com/conorgil/2fa-notifier). Website-support notifications are therefore not a novel invention. [2FA Directory API v4](https://2fa.directory/api) documents methods, documentation links, local caching, MIT data attribution and optional PGP signatures. This preview bundles 2,450 domains from the v4 all-sites API with its retrieval time and source SHA-256. HTTPS retrieval was used; PGP was investigated but not verified. The distinction is recorded in the shipped provenance file.

Manual lookup uses activeTab. Automatic badges explicitly request tabs URL visibility, do not request site contents, and store no browsing history. Matching observes both public and private suffix boundaries and exact domain labels. A support badge never asserts the user enabled 2FA. The [passkey directory](https://passkey.2fa.directory/) was considered as an additional source but is not bundled or claimed as supported here. No inferred passkey support is synthesized from a U2F listing.

## WebAuthn and native integration

[Chromium’s origin guidance](https://chromium.googlesource.com/chromium/src/+/main/content/browser/webauth/origins.md) explicitly supports extension pages and recommends omitting RP ID fields. [WebAuthn PRF](https://w3c.github.io/webauthn/#prf-extension) supplies the secret required for key unwrapping. Newer [capability detection](https://developer.chrome.com/blog/passkeys-client-capabilities) can describe browser features, but actual PRF results and repeatable decryption determine enrollment success here. We do not infer Windows Hello, Touch ID or FIDO2 compatibility from a user agent.

Native messaging would require a signed per-OS companion, installer, origin allowlist, secure IPC and platform-protected wrapping key. That added attack surface is not justified for this preview; no companion is shipped or downloaded.

## Naming

Preliminary public searches considered Lykvakt, Vellum OTP and Tessera. “OTP vault” is descriptive and already appears in other products; [Tessera](https://github.com/privum-cloud/tessera-mfa-app) is already an authenticator name. No final distinctive name or trademark ownership is selected. An empty search result for a candidate is not legal clearance. Formal register searches in intended markets, package/store/domain checks and legal review remain necessary before committing to a brand. The original geometric icon is provisional and uses no service logos.

The implemented differentiation is transparent local architecture and an explicit file-based restoration rehearsal. Whether users prefer it, or whether its security is superior, remains unproven.

## Lykvakt working identity, 24 October 2026

The user selected Lykvakt, a coined Nordic-inspired name. Exact-name web searches for Lykvakt with app/software/authenticator terms surfaced no matching product in this preliminary screen. This is not exhaustive trademark clearance. Vardr and Runvakt were avoided because existing software/security uses surfaced. The original angular lock uses a split keyhole, shock pink #ff1683 and near-black #080608. Material-inspired light/dark/system/AMOLED surfaces use readable pink accent variants.

Google transfer decoding follows [Aegis’s published proto schema](https://github.com/beemdevelopment/Aegis/blob/master/app/src/main/proto/google_auth.proto). Chrome’s [tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-captureVisibleTab) and [activeTab permission](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) describe the temporary access used for explicit capture and filling. No cryptographic primitives were added.
