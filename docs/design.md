# Design and recovery

Keep independently verified backups and your service recovery codes. TOTP codes can be phished, and a compromised device or hostile extension update can read unlocked data. There is no password reset, escrow or recovery server.

## Before updating

Export your accounts from the old version before updating. Earlier previews cannot be opened by this version because the format changed intentionally.

1. Open the working old version and unlock it. If you no longer have it, reinstall the old version in the same folder (same extension), export your accounts, then update.
2. Choose Recovery → Export plaintext OTP links and enter its master password.
3. Keep that file private: anyone holding it can generate the same codes.
4. Open this version, confirm erasing the old local vault only when ready, and create a fresh vault.
5. Choose Import accounts, review the OTP-link file, and save.
6. Compare the accounts and codes, save and test an independent encrypted backup, then remove temporary exports.

Lykvakt vaults and backups protected with PBKDF2 are not supported. There is no legacy reader, password-encoding fallback or automatic data migration. Before doing any password work, the extension recognises earlier envelopes and shows the migration instructions. It doesn't offer older-revision recovery for those files. Selecting an old backup shows the same explanation.

Choosing **Erase the old vault and start fresh** asks for a second confirmation. Both local encrypted records are deleted in one transaction, and only if they still match the records you agreed to erase. A concurrent change cancels the deletion. No files outside this browser are deleted.

## Small, offline architecture

A single TypeScript/Vite extension page holds the Session, DOM and keys. It locks when hidden or closed, when another tab is activated, after the idle timeout, and before opening another window. Closing the popup discards its unlock key. The browser doesn't provide a guaranteed signal for an operating-system lock.

The manifest permissions are exactly ["clipboardWrite"]. There are no host or optional permissions, background scripts or service workers, content scripts, developer backend, advertising, subscriptions or telemetry. There is no externally_connectable setting or external-message handler. The extension never reads or changes web page content. Copying requires an explicit click, or a non-empty search followed by Enter. The confirmation names the account. Clipboard history and other apps may retain the copied value.

Ctrl+Shift+Y is the suggested popup shortcut, or Command+Shift+Y on Mac. You can change it at chrome://extensions/shortcuts. Keyboard-layout shortcuts, the operating system and other extensions may still conflict with it. Outside a dialog, Escape clears a search first and then closes the popup. In a dialog, Escape closes it and cancels its pending work.

Account creation and import forms load when the unlocked account view opens, so they stay out of the locked popup's initial code. Format readers, encrypted-import support, scrypt, Steam code generation, QR image scanning and export, generated-passphrase words and the Argon2 implementation load only when used. Chrome 120+ supports module preloading natively, so the build leaves out Vite's unused fetch-based preload fallback. The package guard rejects network APIs in bundled code.

All runtime code is bundled locally; no WebAssembly or remote code is shipped. The strict CSP allows local scripts and styles, and local/data/blob images. It blocks remote and inline scripts, evaluated code, external fetch/socket connections, frames, objects and form destinations. Build checks enforce the permissions, CSP and bundled-code restrictions.

Runtime dependencies are pinned to exact versions: @noble/hashes supplies Argon2 and the lazily loaded scrypt modules, alongside jsQR and QRCode. Their license notices and the EFF wordlist attribution are packaged in licenses/. Build tools are separate from the extension runtime.

## Format and keys

The envelope uses format "otp-vault", version 2. Every header field is authenticated: format, version, kind, vault ID, revision and the entire password slot. The slot contains kdf, m, t, p, salt, iv and wrapped; the encrypted payload contains key, iv and ciphertext. Extra or missing keys are rejected.

New slots use Argon2id v0x13 with 65,536 KiB (64 MiB) of memory, three passes, one lane and a 32-byte output. Stored costs must be integers within 19,456–262,144 KiB, two–ten passes and exactly one lane. Validation rejects costs outside those bounds before allocation. There are no strength choices, calibration or unlock-time upgrades.

Passwords use NFKC-normalized UTF-8 only, and new passwords must be 14–1024 characters long. The optional generator chooses seven words from the EFF wordlist using browser-provided random bytes and unbiased rejection sampling.

The random 32-byte vault key is imported as a nonextractable AES-256-KW key. A nonextractable AES-256-GCM key derived from the password protects it, using a fresh 32-byte salt, 12-byte IV and 128-bit tag. The password wrapper's AAD binds the format, version, purpose, ID, kind, salt and all password costs.

Each save generates a fresh AES-256-GCM content key and 12-byte IV. It authenticates the canonical header, encrypts the validated data once and wraps the content key with the vault key. The content key is extractable only for that wrapping operation. Recovered content keys are nonextractable.

Canonical JSON sorts object keys by plain code-unit comparison and preserves array order. Account snapshots use the same deterministic comparison.

Payload schema 3 contains accounts, verifiedAt and verifiedSnapshot. Each account has exactly id, issuer, label, secret, type, algorithm, digits, period, counter, favorite and group. The type is totp, hotp or steam. Steam records require a canonical Base32 secret, SHA-1, five characters, a 30-second period and counter "0".

Existing vaults in the current format still open. Older builds reject Steam records, and earlier schemas show the same old-format screen. IDs must be unique, counters are precise unsigned 64-bit strings, and files, account counts and text fields have limits. Website associations and earlier payload schemas are rejected.

## Derivation and locking

A bundled module Web Worker handles one password derivation at a time. It derives the password key, imports it immediately and returns only a nonextractable CryptoKey. Node tests and benchmarks explicitly inject the real yielding engine. The extension ships that engine only in its worker. If the worker is missing or fails to start, the app shows an error rather than deriving on the main thread.

Locking aborts pending work, terminates the worker and changes the Session epoch. A late result cannot reopen the session, save data or expose a secret. Closing a dialog, pressing Escape or replacing it cancels the work started in that dialog, including password workers and storage transactions that can still be aborted. Closing cannot undo a write that has already committed. Raw key, password and decoded payload buffers are cleared in finally blocks where practical.

JavaScript strings, library internals, browser-managed copies, garbage collection and OS paging mean that complete zeroization cannot be guaranteed. Nonextractable keys also cannot protect an unlocked page from hostile code.

Use a long, unique password. Argon2's memory requirement makes offline guessing more expensive, but the time it takes to unlock on your device doesn't tell you an attacker's GPU cost.

## Saving, conflicts and older revisions

IndexedDB stores active and previous in the same existing object store. An ordinary commit keeps the previous encrypted envelope byte-for-byte in the same strict transaction as the new active write. Both changes succeed or neither does.

The compare-and-swap check uses the actual active ID and revision. Concurrent saves are rejected. A typed StorageConflictError rejects a stale save without replacing the Session snapshot; lock and unlock before trying again. Unlock rechecks the selected record after derivation and doesn't write to storage.

If active is structurally damaged or missing, the app can offer a valid previous revision in the current format. It never selects that copy silently: you must choose recovery and enter its password. An incorrect password never triggers fallback.

An older copy can be missing recent changes. HOTP counters may be behind, so don't reuse a code you've already submitted. The next save promotes the recovered copy while still comparing it against the actual active record.

Recovery numbering uses the active revision only when it is a nonnegative safe integer below Number.MAX_SAFE_INTEGER - 2. Unusable revisions are ignored for numbering, but cannot bypass conflict checks. There is no trusted anti-rollback anchor.

Changing the password first verifies the current password, then generates a fresh vault key and password slot and commits the resealed data atomically. The same transaction deletes previous, so the recovery copy cannot retain the superseded key. If it fails, both stored records and the old Session key remain unchanged. The next ordinary save keeps a copy under the new key. Old exports kept elsewhere cannot be revoked.

## Codes and compact controls

Each account has one compact row. Clicking or pressing its copy target copies the current code without revealing it. A separate code button reveals or hides it and has an accessible name. Revealed codes hide again after 30 seconds, navigation or locking. **Always show codes** is optional and starts off.

A 22 px stepped ring shows the TOTP period. It has a full-circle track and a thin arc that depletes clockwise from 12 o'clock. During the last ten seconds, a whole-second number appears inside it; during the last five, it also turns pink. There is no spinning animation or transition, including with reduced motion.

HOTP rows show their counter instead. Fixed lanes keep names, codes, the ring or counter, and **More** separate at widths of 360, 400 and 480 px. Long names and counters are clipped, with full tooltips and accessible names. Rows stay 56 px tall, including the next-code preview. **More** is a native details disclosure with a minimum 36×36 px target. It contains Edit, favorite and confirmed counter advancement.

The optional next-code preview starts off. It stays hidden with the current code and supports custom periods, six/eight digits and SHA-1/256/512. It isn't shown for HOTP accounts, and Copy always uses the current code.

The interface uses system fonts, tabular numerals, a black-and-pink palette and visible focus indicators. Contrast tests cover text, controls and borders. Reduced-motion mode has no animations, and native help and disclosures work by keyboard. Passing axe doesn't certify all aspects of accessibility.

## Backups and moving accounts

Creating an encrypted backup asks you to verify your master password again. The backup has independent key material and its own password. Save it outside this browser and keep its password separately. This version needs current-format files; use the export/import steps above for older preview files.

**Verify or restore a backup** opens the file you select in memory, validates every account and generates test codes. It compares the account snapshot without replacing your accounts. Only an exact match marks the current snapshot as verified.

The backup reminder appears when you haven't verified a backup or when your accounts have changed. Advancing an HOTP counter intentionally changes the snapshot. The app can't tell whether an external file you previously tested still exists.

Recovery in a fresh browser profile creates an independent local vault only when none exists. You can review a different backup for a safe merge; conflicts aren't silently overwritten.

OTP links preserve the OTP settings. Steam uses the documented Ente otpauth://steam host with explicit digits=5 and period=30, which only compatible destination apps can read. Per-account transfer QR and bulk plaintext export require your master password again. These exports contain secrets and don't preserve every app's groups or favorites.

Colons, surrounding spaces, an unprefixed dot segment or ill-formed Unicode in a name require your approval of a transfer name; saved account names stay unchanged. To keep long OTP links within the existing 5,000-character reader limit, the writer can omit the repeated issuer prefix while retaining the issuer parameter.

Google transfer decoding counts every field, including unknown ones. A message can have at most 2,032 fields, and an account can have 32. Known byte fields have their own limits: 4,096-byte account messages, 640-byte secrets, 2,048-byte names and 800-byte issuers. Unknown fields within the budget are skipped without keeping or copying their bodies. Known byte fields share the bounded input buffer, which is cleared after parsing. Large encrypted binary fields use a linear Base64 scan, with decoded-size checks before allocation.

The table below lists supported formats and the source contracts used to implement them. The preview reports every skipped entry and asks for confirmation before saving. Battle.net and unsupported variants are rejected or reported explicitly. Passwords, trade secrets and unrelated fields aren't copied into accounts.

Compare the destination's codes and settings before retiring your existing authenticator. Import compatibility tests don't establish interoperability with every phone app.

## Verification and measurements

Run npm ci --ignore-scripts, build, lint, format:check and test as described in the README. The suite covers known-answer Argon2id/OTP vectors, tampering and bounds, key rotation, backup verification, storage conflicts and rollback, explicit recovery, masking and cancellation.

Parser fuzz tests run 80,000 deterministic, bounded mutations. Each call must return a valid result or throw an Error within the existing per-call budget. The tests exercise malformed inputs; they aren't an exhaustive adversarial review.

Browser CI loads the unpacked extension with synthetic accounts. It checks keyboard flows, menus and account rows, compact height, masking, old-format refusal and confirmed erasure, axe, and locking when you switch tabs in a real browser with a visible window.

For the imports-1 PR, CI also built the pre-change main revision and measured both popup documents on the same runner. First interactive paint means the first paint opportunity after a password field and enabled primary button exist. Repeated fresh popup-document pages use the same warmed browser profile. Results include first-contentful-paint entries and end-to-end unlock samples. They don't measure the physical toolbar or window compositor, or establish performance across devices.

Manual screen-reader use, physical shortcut activation and conflicts, performance across devices, exhaustive app interoperability, long-duration storage tests and an independent security audit remain unverified. The extension screenshots in screenshots/ use synthetic accounts.

The Bitwarden converter reads only the login type, display name and TOTP field. JSON parsing necessarily loads the source file into memory, but the converter doesn't read or retain copies of passwords, usernames, URLs, notes or other secrets. The form clears the raw source text after preview; JavaScript garbage collection cannot guarantee erasure. Non-OTP items are reported as skipped.

FreeOTP's image, color, lock and alternative-issuer presentation parameters are discarded, and no image URL is fetched. FreeOTP+ writes period=30 on HOTP links; the import adapter removes that irrelevant field. Duplicate parameters still fail. Its issuer=Steam/five-character convention is recognised. Explicit otpauth://steam links require digits=5 and period=30; no encoder parameter is guessed. Raivo JSON must be extracted from its archive first, because Lykvakt doesn't open archives.

Aegis uses scrypt followed by AES-256-GCM to unwrap a 32-byte master key, then decrypts the database with a separate nonce and tag. Costs are checked before derivation: power-of-two N from 2 to 65,536, r from 1 to 8, p from 1 to 4, N × r × p at most 524,288, at most four password slots/eight total, and at most 65 MiB of temporary scrypt memory. These bounds allow imports; they aren't recommendations for new passwords. Noble's async path yields about every 8 ms and checks the lock signal in progress callbacks. Cancelled library work wipes its scratch buffers, and derived and master key bytes are cleared in finally blocks.

2FAS schema 4 uses the source's fixed PBKDF2-HMAC-SHA256 cost of 10,000 iterations, a 32-byte AES-GCM key, 12-byte IV and 128-bit tag. The encrypted fields are Base64 ciphertext+tag, salt and IV, separated by colons. Salts are bounded to 16–256 bytes; the Android writer uses 256. The reference is authenticated before the services. Passwords use the source's raw UTF-8 encoding without Lykvakt normalization.

Web Crypto work cannot be interrupted internally, so signal checks discard late results. The UI clears the source password on success or failure, and locking cancels preview and save. The source file is never overwritten.

## Steam support

The algorithm follows [ValvePython's published Steam Guard implementation](https://github.com/ValvePython/steam/blob/master/steam/guard.py#L500): HMAC-SHA1 of the 8-byte big-endian 30-second counter, dynamic truncation, then five least-significant base-26 positions using 23456789BCDFGHJKMNPQRTVWXY. Frozen synthetic vectors were generated by executing that Python function with stdlib HMAC; tests also calculate codes independently with Node/OpenSSL at period boundaries. This is not validation against Valve's live service.

The .maFile reader converts its Base64 shared_secret to canonical Base32. It imports only the sign-in secret and account_name, leaving out trade and market confirmations, identity secrets, session tokens and revocation data. Steam's own app doesn't display its setup secret; that usually comes from another authenticator or a .maFile. Keep a working authenticator until you've checked sign-in. The import and manual account forms include the same explanation.

## Moving from Authy / Microsoft Authenticator

Neither app offers an official export of its sign-in setup secrets. [Authy's support index](https://help.twilio.com/sections/19752375651355-2FA-Account-Tokens) lists token export as unsupported. Third-party Authy tools can produce OTP-link lists; use them at your own risk and with test accounts first. Lykvakt does not provide or verify those tools. For Microsoft Authenticator, re-enroll each service from its security settings; [Microsoft's export documentation](https://support.microsoft.com/en-US/authenticator/export-passwords-from-microsoft-authenticator) covers passwords, not these setup secrets. Keep your existing authenticator until every service works.

## Formats that aren't supported

Encrypted andOTP, Bitwarden, Ente, Proton and Stratum exports, native FreeOTP backups, ZIP/HTML archives and Proton Steam entries remain unsupported. The readers don't implement those encryption or serialization formats. Unsupported account kinds are reported rather than silently converted. Bitwarden steam:// fields are rejected; use Aegis or .maFile for Steam instead. There is no Authy or Microsoft secret parser.
